# UU Remote Ubuntu 鼠标光标修复记录

生成时间：2026-07-28 23:45:02 HKT

## 结论

这次问题主要位于 Ubuntu 被控端的兼容桥接层：

```text
Windows UU 主控端
  -> Wine 中的 GameViewerServer.exe
  -> 私有 Xvfb :20
  -> Windows SDL FreeRDP
  -> GNOME RDP
  -> Ubuntu 物理桌面
```

不是 Windows 主控模式设置未生效，也不是 Ubuntu 物理鼠标损坏。
需要修改拉取下来的仓库代码，单独调整 UU 客户端设置无法完整解决。
修复已经写入源码；最新安装器将 cursor guard 作为显式 opt-in，只有
`UURB_CURSOR_GUARD=on` 时才会注入。需要该兼容层的主机可持久化启用，
不受影响的主机继续使用原始 UU 光标路径。

当前 Ubuntu 被控端继续使用经过审计的 UU Remote `4.33.0.8907`。
本次没有因为鼠标问题强制升级到尚未重新完成冷启动验收的
`4.34.0.8979`。

## 原因

问题分成两层。

### 1. 鼠标被窗口抓住

内层 SDL FreeRDP 默认允许相对鼠标和窗口抓取。鼠标进入全屏中继
窗口后，可能无法移出控制区域。

修复参数：

```text
/mouse:relative:off,grab:off
```

这使桌面控制保持绝对坐标，同时关闭 SDL 的独占抓取。

### 2. 光标可以操作但不可见

实际 UU 会话日志持续出现：

```text
Unable to get cursor icon info. Error = 1402
```

Windows 错误 `1402` 是 `ERROR_INVALID_CURSOR_HANDLE`。FreeRDP 创建
的 HCURSOR 属于另一个 Wine 进程，UU 的 `GameViewerServer.exe` 和
`streamer.dll` 无法可靠地读取该句柄。

同时，GNOME RDP 偶尔会发送隐藏光标指令。SDL FreeRDP 将其转换为
`SetCursor(NULL)`，Wine/X11 随后使用透明光标。UU 再把这个状态传给
Windows 主控端，因此即使选择了主控模式，光标仍可能消失。

输入链路本身没有丢失：诊断期间记录的鼠标注入为 96/96 成功，
均为 `result=1, error=0`。

## 实现

新增 `src/uu_cursor_guard.c`，构建为：

```text
uu-cursor-guard.dll
```

同一个 DLL 只注入两个指定进程。

### SDL FreeRDP 侧

- Hook `USER32!SetCursor`。
- 正常的非空 cursor 原样传递。
- `SetCursor(NULL)` 改为进程内有效的系统箭头 `IDC_ARROW`。
- 不修改 `ClipCursor`、`ShowCursor` 或 Wine 全局注册表。

### UU 捕获侧

- 注入 `GameViewerServer.exe`。
- Hook 主程序及 `streamer.dll` 的 `GetCursorInfo` 和 `GetIconInfo`。
- 将跨进程无效 HCURSOR 转换为 UU 进程内有效的系统箭头。
- DLL 初始化时执行一次完整的 cursor reader 自检。

这会优先保证光标始终可见。UU 主控端看到的光标形状可能固定为
标准箭头，而不会完整显示文本输入、缩放等所有远端 cursor 形状。

### 启动与恢复

启用 cursor guard 后，`uu-remote-bridge.service` 每次启动都会：

1. 启动并检查 UU 服务端。
2. 向 `GameViewerServer.exe` 注入 cursor reader guard。
3. 启动 SDL FreeRDP。
4. 向 `sdl-freerdp.exe` 注入 hidden-cursor guard。
5. 确认两个 guard 都已初始化，再开放正常使用。

任一注入或自检失败，桥接会退出并由 systemd 完整重建，避免显示为
在线但光标保护实际未生效。

## 验证

- compatibility DLL 使用 MinGW x64 严格告警构建成功。
- 当时的 `91` 项 Python 单元测试全部通过；后续仓库测试继续覆盖该路径。
- `scripts/verify.sh --quick` 全部通过。
- guard 同时出现在 SDL FreeRDP 和 GameViewerServer 的进程映射中。
- UU 读取侧 `GetCursorInfo -> GetIconInfo` 进程内自检通过。
- 服务冷启动后两个 guard 均自动恢复。
- 180 秒内连续采样 900 次，全部为 `32x32` 可见光标。
- UU、托盘、XRDP、物理桌面 VNC、TeamViewer 均保持 `active`。
- 用户从 Windows UU 重新连接 Ubuntu 后确认光标表现已经恢复。

## 后续尺寸修复

诊断时物理 GNOME 桌面使用约 150% X11 分数缩放，实际 Xcursor 为
`48x48`；Wine 仍按 96 DPI 创建默认 `32x32` 系统箭头。原 guard 为
解决跨进程句柄失效而强制返回这个默认箭头，因此 UU 的独立光标通道
会把正常的 `48x48` 光标降为 `32x32`。视频分辨率变化会影响观感，
但不是光标消失的主因。

guard 现使用 `CopyImage` 创建指定尺寸的进程内箭头，并验证返回
bitmap 的实际宽高。启动器默认以 `UURB_CURSOR_SIZE=auto` 读取物理
桌面的 `Xcursor.size`；也可在持久化环境文件中将其设置为 `24` 至
`128` 的固定值。本机最终采用 `64`，不修改桌面分辨率或 Wine 全局
DPI。

2026-08-02 的后续调查确认，150% X11 分数缩放与持续 GNOME 桌面捕获
组合会触发另一类 Mutter `MIT-SHM` 崩溃。当前主机已改为原生 100%
画布，文字、桌面图标和 Dock 分别独立补偿到 `1.5`、`large`（96 px）
和 57 px。这组设置与 cursor guard 的 64 px 独立光标尺寸没有耦合。
详见 [GNOME Shell capture crash record](gnome-shell-capture-crash-20260802.md)。
